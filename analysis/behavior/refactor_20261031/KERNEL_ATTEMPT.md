## 为什么门禁没跑通

尝试了两版脚本：

**第一版 `gate.m`**：直接调 `SAR20('run')` 再读 `spectrum.mat`。
失败原因明确 —— **当前模型工作区的 P 是 N=8**，而 `SAR20.m:226` 只在
`P.N>=256` 时才生成 `spectrum.mat`。N=8 时 `spectrum_status='not_run_short_capture'`。

**第二版 `gate2.m`**：先 `load` 历史基线 P（N=256）再 `SAR20('apply',P)` 再 `run`。
任务执行了（`LastTaskResult=0`），但**没有产出结果文件**。
两次相邻 run 目录确实生成了（14:47:15、14:49:53），说明 `run` 本身在跑，
但 `gate2` 的后续步骤（`load spectrum.mat`）没有落地到 JSON。

根因未确定。可能是 `apply` 改变了模型状态导致后续步骤出错，也可能是
`load(...,'P')` 在这份 `-v7.3` 参数文件上耗时/失败。

## 决定：回滚

按用户指示**立即回滚**。理由：

1. 这是 RA/AZ 物理核心，**未通过数值门禁的内核改动不应留在生产路径**
2. Token 级等价虽然通过，但那只证明"代码语义没变"，不证明"整图行为没变"
3. 回滚成本极低，备份就在手上

## 这轮真正的收获

**基线本身是成立的**（见 `BASELINE.md`）：
模型经证明逐位确定性，9 组同配置 run 的 5 项指标跨度为 0。

**缺的只是"用给定 P 跑一次并读回指标"这条执行链路没调通。**

或者直接检查 `apply` 后 `ws` 里的 P 是否真的变成 N=256）验证链路，
而不是一上来就跑 75 秒的完整仿真。
